## Sub-Topic 1 - Clean Code
The importance of clean code and what it is. 

* Bad, messy code can slow development making it difficult to fix bugs and opens the door to more attacks.
* Clean code has several components: it's readable and understandable by other people, it's simple and direct, it's easy to change and extend, and it's free of duplication and unnecessary complexity.
* Clean is not just a skill, it takes discipline and a good mindset.
* Clean code can make future changes faster and easier, reduces bugs, enhances team collaboration, and extends the life of the software/project/app.

<br>

## Sub-Topic 2 - Integrating with Linters
What Linters are when to use them. 

* Linters include formatting rules and bug finding rules.
* The formatting rules of linters become unnecessary and conflict with Prettier.
* Linters are meant for code quality and errors whereas Prettier is meant for formatting.
* Using something like eslint-config-prettier turns off the ESLint rules that clash with Prettier formatting.
* Not recommended to run Prettier inside a linter, has lots of formatting errors, slower performance, and extra complexity.

<br>

## Sub-Topic 3 - Organizing your CSS
Why you should organize your CSS. 

* CSS organization is your responsibility as a developer because it has no built in structure.
* Follow a consistent style guide.
* Structure the stylesheet logically: General/global -> utility -> site-wide -> page/component-specific
* Avoid overly specific selectors because they are hard to reuse, may cause duplication, and make overrides difficult.
* Using multiple CSS files is good for big projects to improve organization and reduce merge conflicts.
* Use a naming methodology to create predictable, modular class names, make components easier to understand and reuse (like BEM: blcok-element-modifier).
* Separating reusable objects/patterns and extending them with small variations reduces duplication and improves scalability.
* Other tools can help with organization, like Sass.

<br>

## Sub-Topic 4 - Pareto Principle (80/20 rule)
80% of results come from 20% of causes.

* A small number of inputs can make the biggest outcomes, and identifying those help you focus your effort where it matters most.
* It is a prioritization tool. 
* For productivity: list all tasks, identify the few that create the most impact, do those first
* For decision-making: identify problems, find causes, group related causes, rank by impact, fix top 20% that will solve most issues
* For quality control: Pareto charts help visualize causes that create the most defects so the team can see which to fix first.
* Benefits help prioritize tasks, making the priority order clearer, which improves productivity all the way through.

<br>

## Sub-Topic 5 - Code Comments
An explanation of code comments and why they are helpful/useful. 

* Comments are a good communication tool between developers.
* Good comments add context that code cannot express, but bad comments create noise and confusion.
* Good comments explain why not what. (Explain things like business rules, product decisions, and reasoning behind an approach).
* Can provide formal documentation can be used to describe parameters, returns, errors, or be used to auto-generate API docs.
* Comments can mark fragile code, strict dependencies, and critical timeouts.
* Bad comments are redundant, restating the obvious of what the code is doing.
* Comments can include humor but should not replace real documentation.
